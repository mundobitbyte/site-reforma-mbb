Cantina Horizonte · laboratório

11 — Qualidade e integrações

A resposta de sucesso precisa corresponder ao que foi salvo.

Qualidade que não cabe só na tela

Confiabilidade: a venda e o estoque não podem ficar pela metade. Integridade: itens precisam apontar para registros existentes. Privacidade: a consulta local não deve ganhar dados pessoais sem necessidade. Acessibilidade: ações precisam ser compreensíveis e utilizáveis por teclado. Desempenho exige condições e medidas; não declaramos uma meta atingida sem experimento.

Autenticação pergunta quem é a pessoa; autorização pergunta o que pode fazer. Os papéis do desenho não implementam nenhuma delas. Este laboratório só usa dados fictícios e execução local; acesso real exigirá outra análise de segurança.

O histórico mantém transição e data, mas não identifica atendente. Isso é um limite, não auditoria completa.

Interface, API e banco conversam

API é a interface de conversa entre programas. A tela envia JSON de itens/cupom; o serviço valida; o banco confirma a transação; a API devolve o pedido salvo. O servidor não confia no subtotal exibido pelo navegador.

Timeout é esperar além do limite; retry é tentar novamente. Se uma resposta se perder depois de gravar, repetir POST pode criar outra venda: o pedido ainda não tem chave de idempotência. Desabilitar um botão não resolve todas as repetições entre clientes. No avanço de estado, o estado esperado impede repetir o mesmo passo com consulta antiga.

Notificações, webhook e serviços externos ficam fora da entrega atual. Antes de adicioná-los, decida o que ocorre se falharem e se devem esperar resposta síncrona ou operar separadamente. Não marque o pedido entregue porque uma mensagem foi enviada.

Entenda a conversa sem programar

JSON é texto estruturado para trocar dados: chaves nomeiam valores; colchetes agrupam uma lista. POST é uma solicitação HTTP usada aqui para criar pedido. HTTP é o protocolo da conversa entre navegador e servidor. Timeout significa que a espera terminou sem resposta; isso não prova que o banco deixou de salvar. Idempotência significa que repetir a mesma operação tem o mesmo efeito de executá-la uma vez.

Ver exemplo didático — não é evidência de execução

E12, exemplo didático de JSON: {"itens":[{"produto_id":1,"quantidade":2}]}. A tela solicita criar o pedido; servidor valida; banco salva; resposta traz número/total. Se salvar e a resposta se perder, repetir POST pode criar duas vendas: este contrato não garante idempotência de venda. Uma chave única por tentativa é uma possível melhoria a analisar, não recurso já implementado.

Sua prática e conferência: Descreva a sequência de sucesso e o caso de resposta perdida, sem enviar requisições reais. Registre garantia, limite e decisão segura: consultar antes de repetir cegamente. Confira que aparência da tela não comprova gravação.

Onde registrar: Caderno de Análise, etapa 11 (E12). Copie a seção correspondente para seu documento ou folha; este site não salva respostas.
