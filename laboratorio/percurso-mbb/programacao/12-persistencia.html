12 — O terminal usa o mesmo serviço e banco

A simulação precisa chegar a uma venda fictícia persistente sem copiar todas as regras para o terminal.

Ligação com a aplicação

Você está examinando como o mesmo pedido é salvo. Leia primeiro Conceitos que resolvem esta necessidade; depois acompanhe a chamada do terminal ao serviço Cantina. A confirmação vem após validar e gravar o pedido, não apenas calcular um total na tela.

Antes de programar

A simulação precisa chegar a uma venda fictícia persistente sem copiar todas as regras para o terminal.

Pré-requisitos: Etapas 0–11. Os modelos e BD são referências opcionais do mesmo caso; a preparação necessária está abaixo.

Conceitos que resolvem esta necessidade

contrato do serviço, parâmetro SQL, transação, adaptador de terminal, argparse.

Em palavras simples: o terminal recebe seu comando; o serviço confere as regras; o banco guarda o resultado. Uma transação reúne as gravações para confirmar tudo ou reverter se algo falhar. A preparação está logo abaixo, antes dos comandos.

Agora use terminal.py, no mesmo projeto do serviço. Essa interface converte argumentos e apresenta resultados; Cantina mantém validação, consolidação, preço histórico, cupom, estoque e transação.

argparse, da biblioteca padrão, lê comandos e opções. --item 1:2 significa produto 1, quantidade 2; repetir a opção envia outra linha. A conversão é do terminal; faixa, produto e saldo são conferidos pelo serviço. Valores SQL são ligados aos placeholders ?, separados do texto do comando.

O banco desta prática fica em laboratorio/cantina-evolutiva/dados/programacao/cantina.sqlite3. Ele usa o mesmo schema e migrações, com dados fictícios; preserva o banco da interface Web e a prática de BD. Preparar é feito uma vez e recusa recomeçar um banco existente. Não passe caminho externo ao CLI.

  1. Na cópia experimental, abra laboratorio/cantina-evolutiva e siga a preparação desta página. Confira terminal.py, servico.py e requirements.txt; se não aparecem, você está na pasta errada.
  2. Na pasta laboratorio/cantina-evolutiva, com o ambiente ativado, execute os comandos abaixo um por vez.
  3. Anote o ID retornado pelo registro. A consulta 1 abaixo só corresponde à primeira venda em um banco novo.
  4. Feche e reabra o terminal, reative o ambiente e consulte esse mesmo ID. Não repita registrar só para conferir: cada sucesso cria outra venda.

BEGIN IMMEDIATE inicia a escrita antes de ler o saldo usado na venda. Gravação de pedido, item, estoque e eventual cupom é confirmada ou revertida em conjunto. Retome a evidência BD07. Contar linhas não prova a interface Web ou o comportamento de várias pessoas.

Comece e confira

O terminal é a interface de texto; o serviço verifica as regras; SQLite guarda o pedido num arquivo. Você não precisa escrever SQL nem iniciar um servidor Web para esta atividade. Os dados são fictícios e ficam separados da prática de BD.

Preparar o ambiente na pasta cantina-evolutiva

Abra o CMD nessa pasta no Windows, como na etapa 0. Se já existe uma .venv funcional nela, apenas ative. Se não existe, crie uma vez:

Windows CMD: criar somente se faltar

py -m venv .venv

Windows CMD: ativar

.venv\Scripts\activate.bat

Linux/macOS: criar somente se faltar

python3 -m venv .venv

Linux/macOS: ativar

source .venv/bin/activate

Use os comandos do seu sistema. Com o ambiente ativado, python deve apontar para ele; a instalação abaixo atende o fuso usado pelo serviço em sistemas sem essa base:

Instalar a dependência do serviço

python -m pip install tzdata

Conferir ambiente: True e America/Sao_Paulo

python -c "import sys; from zoneinfo import ZoneInfo; print(sys.version); print(sys.prefix != sys.base_prefix); print(ZoneInfo('America/Sao_Paulo'))"

venv separa pacotes; não muda o código nem os dados. Se a criação falhar, resolva a instalação do Python antes do registro. Não copie um ambiente virtual de outro computador.

  1. Rode os cinco comandos da prática, um por vez. preparar apenas na primeira vez; se o banco existe, consulte o cadastro sem reiniciar.
  2. registrar mostra um objeto JSON com id, status, valores e itens. Anote o ID real: 1 só vale para a primeira venda em banco novo. Cada registro aceito cria outro pedido.
  3. Feche o terminal. Abra de novo na mesma pasta, reative a mesma .venv e rode consultar com esse ID. O pedido precisa continuar lá.
  4. Confira status antes de avançar. A opção --estado-esperado Novo só serve se esse for o estado consultado. Repeti-la após Confirmado deve recusar, sem criar outro evento.
Ver exemplo didático — não é evidência do aluno

Banco novo: 2 águas → pedido 1, Novo, total 600; consulta em outro processo recupera o mesmo pedido; avanço → Confirmado. Um estoque exibido ou subtotal calculado sozinho não comprova essa gravação.

Em PG12 registre ID, total, consulta após reabrir, estado antes/depois e recusa ao repetir o estado antigo. BEGIN/COMMIT/ROLLBACK são iniciar/confirmar/reverter a transação: aqui o serviço cuida de gravar pedido, itens e saldo juntos. O aluno não precisa dominá-los antes deste primeiro uso.

Prática com código completo

Criar uma vez

python terminal.py preparar

Consultar cadastro

python terminal.py produtos

Registrar primeira venda fictícia

python terminal.py registrar --item 1:2

Consultar ID retornado

python terminal.py consultar 1

Avançar com estado conferido

python terminal.py avancar 1 --estado-esperado Novo

Preveja, execute e compare

Banco novo: Água 300/saldo 20; primeira venda 2 Águas, subtotal/total 600, saldo 18. Estado vai de Novo para Confirmado com um evento.

Consulte a venda salva e tente usar outra vez estado-esperado Novo: deve recusar.

Evidência desta etapa

PG12: comando, retorno salvo, reabertura e transição; reusa BD07/BD09/RF-01 a RF-09.

Registre previsão, execução, diferença, limite e reteste no caderno.
