7 — Consultar sem confundir erro HTTP e erro de rede

A tela precisa obter os produtos da fonte usada pela venda e interpretar a recusa.

Antes de construir

A tela precisa obter os produtos da fonte usada pela venda e interpretar a recusa.

Pré-requisitos: WEB00–WEB06; PG08/PG09.

Conceitos por necessidade

fetch, Promise, async/await, Response.ok, json, try/catch, throw, export/import, parâmetro padrão, URL, Error, valor alternativo com ||.

fetch produz uma Promise; await espera seu resultado dentro de uma função async. Receber um status 404 ou 409 não faz Fetch falhar automaticamente: o cliente confere response.ok. response.json() também é assíncrono.

O módulo api.mjs organiza a conversa: montar URL → enviar → ler JSON → interpretar status. export/import compartilham as funções entre arquivos, como os módulos Python, com sintaxe própria de JavaScript. Os arquivos .mjs são módulos; importá-los não envia requisição automaticamente.

No parâmetro opcoes = {}, o objeto vazio é o valor padrão quando a chamada não fornece opções. new URL constrói o endereço da requisição. new Error cria o erro que throw propaga ao chamador; o catch recebe a falha da operação, retomando a ideia de try/except de PG08.

Em dados.detail || "A operação foi recusada pelo servidor.", || devolve o primeiro valor quando ele é verdadeiro na avaliação lógica; caso contrário, devolve o segundo. Uma mensagem não vazia é preservada; uma string vazia usa o texto alternativo. Esse uso escolhe um valor, enquanto a condição de WEB04 escolhia um caminho.

Esses recortes podem ser exercitados com Node em testes, mas a interface da aplicação usa o script já existente. Para ler no navegador, abra a aplicação em http://127.0.0.1:8001/ e observe /api/produtos na aba Rede. Não importe de file:// e tente contornar CORS; origem e forma de execução precisam ser identificadas.

JSON inválido, erro HTTP e falha de comunicação são situações distintas. A nova função mantém o código HTTP quando recebeu resposta. A verificação aqui usa testes dos módulos e HTTP local; não comprova DOM, foco ou tela.

Prática com arquivos completos

api.mjs

// Cliente de exercício: a regra e a gravação continuam no serviço Cantina.
export async function solicitar(base, caminho, opcoes = {}) {
  let resposta;
  try {
    resposta = await fetch(new URL(`/api/${caminho}`, base), opcoes);
  } catch {
    throw new Error('Falha de comunicação. Este cliente não confirmou o resultado; não reenvie uma venda automaticamente.');
  }
  let dados;
  try {
    dados = await resposta.json();
  } catch {
    const erro = new Error('O servidor não devolveu JSON válido para esta operação.');
    erro.status = resposta.status;
    throw erro;
  }
  if (!resposta.ok) {
    const erro = new Error(dados.detail || 'A operação foi recusada pelo servidor.');
    erro.status = resposta.status;
    throw erro;
  }
  return dados;
}

07-consulta.mjs

import { solicitar } from './api.mjs';

export async function consultarProdutos(base) {
  return solicitar(base, 'produtos');
}

export async function consultarPedido(base, id) {
  if (!Number.isInteger(id) || id < 1) {
    throw new Error('Informe um identificador inteiro positivo.');
  }
  return solicitar(base, `pedidos/${id}`);
}

Como executar e conferir

Siga a prática HTTP local: preparação, cardápio, registro único, consulta pelo ID retornado e conflito. Não use ID de outra sessão. Registre a entrada, a resposta real e a confirmação; os valores previstos são exemplos didáticos.

Preveja, experimente e compare

Diferencie resposta 404 de ausência de resposta e explique por que json precisa ser esperado.

Registre o que espera antes de executar. Acrescente resultado real, diferença e limite depois; as verificações de código desta adaptação não são teste visual ou sessão com aluno.
