8 — Registrar uma vez e ler o que foi confirmado

Uma confirmação de venda precisa vir do servidor, não apenas do subtotal calculado na tela.

Antes de construir

Uma confirmação de venda precisa vir do servidor, não apenas do subtotal calculado na tela.

Pré-requisitos: WEB00–WEB07.

Conceitos por necessidade

POST JSON, projeção dos campos, 201, estado de envio, finally, resultado incerto.

O módulo registra apenas produto_id/quantidade e cupom opcional. Produto, preço, estoque, desconto e total são conferidos pelo serviço. Com 2 Águas em banco novo, a resposta de criação é 201 e o total 600 centavos.

A interface completa mantém uma marca de envio, desabilita o botão e, em finally, libera o controle. Ela limpa carrinho/cupom só quando o pedido foi confirmado na resposta. Se a atualização posterior do cardápio falhar, a venda já foi confirmada: a mensagem pede atualizar estoque, sem dizer que a venda falhou.

Desabilitar um botão reduz repetição na mesma tela, mas não garante idempotência. A API não tem chave de idempotência de venda. Se a conexão cair após o banco confirmar, o cliente pode não saber o resultado. Não reenviar POST automaticamente nem afirmar que nada foi gravado. Com ID conhecido, consultar é a conferência.

O módulo de exercício não controla carrinho nem botão; isso pertence à interface. O padrão PRG/sessão do Web II continua útil em seu contexto PHP e não é apresentado como garantia deste POST JSON.

Prática com arquivos completos

08-pedido.mjs

import { solicitar } from './api.mjs';

export async function registrarPedido(base, itens, cupom = null) {
  const entrada = {
    itens: itens.map(item => ({
      produto_id: item.produto_id,
      quantidade: item.quantidade,
    })),
    cupom,
  };
  return solicitar(base, 'pedidos', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(entrada),
  });
}
